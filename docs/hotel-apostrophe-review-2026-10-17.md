## 변경 범위

호텔 별칭을 비교할 때 영문자 사이의 작은따옴표 `'`, `‘`, `’`, `＇`를
생략형과 동등하게 처리한다. 공백 제거 전에 적용하므로 단어 끝의 따옴표,
공백으로 분리된 따옴표, 큰따옴표, 숫자 사이의 기호를 일괄 삭제하지 않는다.
기존 악센트·공백·하이픈·마침표·`&` 처리 기준은 유지한다.

- 별칭 생성·중복 검사·등록 보류·실제 호텔 비교가 같은 비교 키를 사용한다.
- 기존 작은따옴표 표기로 전체 이름이 일치하면 정규화로 새로 일치한 후보보다 우선한다.
- 정규화로 서로 다른 호텔의 별칭이 같은 키가 되면 출처 우선순위만으로 선택하지 않고 확인 필요로 남긴다.
- 짧은 단일 단어 별칭은 다른 단어나 숫자 식별자의 일부로 잡히지 않도록 경계를 검사한다.
- 명시적인 `exact` 별칭은 계속 전체 문자열 일치를 요구한다.
- 운영 불확실·제휴 종료 검사는 원래 표기와 따옴표를 정리한 표기 모두에서 호텔 매칭보다 먼저 실행한다.
- 브랜드 키워드·운영사·보조 토큰 분석·포인트 구매 제외 규칙은 기존 입력과 정책을 유지한다.
- 원본 결제명, 금액, 실제 등급·포인트, 취소·L4/L5 우선순위는 바꾸지 않는다.

## LE DOKHANS 사례

기존 DB의 `PARTX`와 파생 별칭 `Le Dokhan's`를 사용한다. 별도 결제명 별칭이나
신규 호텔을 추가하지 않았다.

| 입력 | 변경 전 | 변경 후 |
|---|---|---|
| `LE DOKHAN'S HOTEL FOH` | PARTX, active/high | 동일 |
| `LE DOKHAN’S HOTEL FOH` | PARTX 후보, needs_review/medium | PARTX, active/high |
| `LE DOKHANS HOTEL FOH` | HOTEL 키워드만 인식, needs_review/low | PARTX, active/high |

이는 이름 기반 호텔 식별 개선이다. `FOH`의 의미나 해당 결제명과 호텔의 직접 연결을
새로 공식 확인한 것은 아니다. 실제 특별적립 대상 여부는 카드사 확인이 필요하다.
해외 L2·양수 차액 조건을 만족하면 기존 정책에 따라 **누락 의심**으로 분류하며,
누락이나 지급을 확정하지 않는다.

## 전체 비교

보존 DB 10,309개는 현재 운영을 전수 확인한 수치가 아니다. DB 자체는 수정하지 않았다.

변경 전 입력을 보관한 후 같은 입력을 새 코드로 다시 계산했다. 비교 단위는
`종류 + 호텔 ID + 입력명 + 거래일`이며, 합성 변형은 실제 사용자 거래 수가 아니다.

| 비교 입력 | 건수 | 결과 |
|---|---:|---|
| 기존 공식명 | 10,309 | 전체 판정 객체 동일 |
| 기존 별칭 | 1,589 | 호텔·확신도·상태·지역 동일; L'Escape의 매칭 근거 표기만 변경 |
| 작은따옴표 합성 변형 | 940 | 752건의 출력 변경, 나머지 동일 |
| 등록 보류 공식명·별칭 | 178 | 전체 판정 객체 동일 |
| 별도 점검 입력 | 11 | Dokhan's 2건 인식 개선; L'Escape 매칭 근거 표기만 변경 |
| 합계 | 13,027 | 판정 객체 변경 756건 |

756건 중 725건은 호텔 식별·확신도·상태 등 의미 있는 값이 달라졌고,
31건은 매칭 근거 등 설명 필드만 달라졌다. 많은 변형이 기존 브랜드 키워드의
`certain`에서 특정 호텔 별칭의 `high`로 바뀐다. 두 확신도 모두 기존 계산 정책상
동일한 누락 의심 조건을 사용하므로 확신도 이름만으로 적립 결과 변화라고 해석하지 않는다.

작은따옴표가 있는 공식명 전체에 대해 5가지 표기(4종 따옴표·생략)의 호텔 식별과
정책이 원래 공식명과 같음을 별도 테스트했다. 서로 다른 호텔 이름을 새로 하나로
합치는 전체 비교 키 충돌은 현재 DB에서 0건이었다. 충돌이 생기는 합성 사례는
확인 필요로 남는지 테스트했다.
